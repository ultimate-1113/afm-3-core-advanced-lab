# 実機結果からの推奨

最初に実装する価値が高いのは、変更箇所や不足情報を人がレビューするための候補生成。決まった項目、短い入力、具体例、公開スキーマを使う。未使用30ケースでは適合6→29件に改善した。ただし10種類の合成パターンの変種であり、実際の資料に同じ正答率を期待する根拠にはならない。

| 用途 | 今回の判断 | 実装する場合の条件 |
|---|---|---|
| 意味の差分・不足検出 | 有望。3分野で最も改善した | 変更対象／不足項目の出力を限定し、具体例を与える。最終判断は出典と通常コードでも確認 |
| 画像から入力候補を作る | 明瞭な合成画像6例では直接画像＋スキーマが6/6 | レシート／予約のフォーム入力候補。型・値を検証。OCR表は座標を保持して行列を復元 |
| 限定された分類 | 初期5/6、短文で約0.27秒中央値 | unknownの選択肢を設け、曖昧な入力は人へ返す。実データの追加評価が必要 |
| 日本語の文案・整形 | 自然な短文を出せる | 数値やIDの保持をコードで照合。指定キーの取り違えと根拠のない形容に注意 |
| 情報抽出 | 今回の調整では改善なし（21→20/30） | 原文と値を照合し、不明はnull。年を入れたら出典に年があることを検査。現在／旧／引用の対応も確認 |
| 表・ファイル操作 | 集計仕様抽出は改善したが18/30、ファイル仕様2/6 | 実行を任せる段階に進めない。候補の操作仕様を表示し、コードで型・列・パス・許可操作を検査 |
| ツール計算 | 必須設定で単純4例は成功、複数演算2例は失敗 | 一回の操作を小さくする。全体式・境界比較・状態管理は通常コードが持つ |
| 長い履歴、厳密なコード理解、最適化 | 元の6失敗例が残る | 今回は採用根拠が得られなかった |

呼び出しはSwift直接APIを主にすると、実機variant・context・usage、構造化ストリーム、DynamicProfile、ツール必須条件、キャンセルを制御しやすい。Python SDKは反復検証・集計向き。常駐Pythonアプリでストリームを使う場合は、scripts/sdk_responsive.pyの専用スレッド化を利用する。SDK0.2.1でイベントループの最大停止約2.5〜3.5秒を約11〜13msへ抑えた。生成自体を速くしたものではない。

既存HTTPクライアントを使うならfm serveをローカルへbindする。今回の短い要求の中央値はSwift約0.41秒、SDK約0.59秒、fm respond約0.55秒、serve TCP約0.28秒、Unix約0.77秒。各5回、設定の完全同等性や順序効果を除けていないため、TCPが常に速い／Unixが遅いという結論にはしない。通信経路の選択は必要な機能と扱いやすさを優先する。

背景処理はまず同時要求1件、TaskPriority.background、短い入力、有限の出力、キャンセルできるキューで開始する。同時2件で速度倍増を確認できず、QoSの明確な効果も今回の小CPU代理試験では確認できなかった。GPUを使う前景アプリや消費電力への影響は未測定。flashを使う構成から無負荷とは判断しない。

入力をコードで関連部分に絞る試験では、入力3315→125トークン、完了中央値約3.18→0.86秒へ短縮し、回答の内容も保持した。全文投入の3例ではJSONフェンスを付けたため、内容の一致と厳密なJSONだけの出力は別評価になる。モデルに要約させてから抽出すると欠落を増やす可能性があるので、今回の結果は「既知の関連部分をコードで選択する」場合に限定する。

prewarmは入力キャッシュを確認できたが、1200ms待機を含む完了時間は増え、TTFTも安定した短縮と断定できない。利用が事前に分かるUIで再測定する。独立要求は新規セッションを基本にし、会話継続は意味上必要なときだけ。履歴復元はKVキャッシュの保存ではない。結果キャッシュはOS build・モデル・指示・入力・生成設定をキーへ含め、古い結果を無条件に使わない。

SDKコードのApache-2.0の範囲では通知・型変換・公開APIの橋渡しを改善できる。Core Advanced本体の重み／量子化／内部カーネルへの改変許諾と対応APIは確認できていない。旧アダプタツールキットもOS27に非対応なので採用しない。詳細はpermitted-improvements.md。
