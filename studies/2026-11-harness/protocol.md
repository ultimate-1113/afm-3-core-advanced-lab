# AFM 3の直接回答とハーネスの比較条件

日本語の合成36問を、Core AdvancedとCloudの両方に出す。機器の最適構成、設定履歴の復元、納品書の突合を各12問とする。前回の結果は課題の選定に用いた。今回の入力・画像・正解・プログラム・採点規則・試行順の生成器を最初の推論に先立ち SHA-256 で固定する。

| 方式 | 入力と処理 | 1問のモデル呼び出し |
|---|---|---:|
| plain | 問題、必要な出力キー、JSONでの回答を日本語で指示。納品書は原画像 | 1 |
| schema | plainと同じ文字列と画像に、返却値のJSON Schemaを指定 | 1 |
| review | schemaの実際の回答と元資料を新規セッションに渡し、見直しを依頼 | 2 |
| feedback | schemaの回答が公開入力に基づく機械検査に落ちた場合だけ、同じ見直し指示に検査理由を追加 | 1〜2 |
| guard | feedbackと同じ応答にもう一度検査を適用し、違反が残れば回答を保留 | 1〜2 |
| program | AFMが依頼の制約、設定操作、または明細行の品番・除外数を構造化。コードが列挙・状態復元・行別加算を実行 | 1 |
| rows | 納品書専用。Visionの文字位置と見出しから行・列を復元し、同じ表を渡してAFMが最終回答まで作る | 1 |
| code | 通常の日本語パターンと同じ実行器を使う。納品書の品番・備考は同じOCRから解釈 | 0 |

基準は各モデル自身のplain。二つの成果を区別する。主指標は指定した内容の全項目一致で、前後の説明やMarkdownが付いても一意なJSONオブジェクトを復元できれば採点する。数値の型、全品番、重複キー・重複品番は厳密に検査する。第2指標として、生の回答全体をそのままJSONとして読めたかを保存する。文章のみの回答を人手で補完する運用は対象外。実行器の途中表現の一致と、最終回答の一致を個別に採点する。保留、拒否、形式不正は主指標の分母に含める。

最適化では在庫、合計値、読めた要求水準と台数上限を検査する。最適解を列挙する処理を再試行の判定に使わない。全項目が実現不能を示す場合、検査はその主張を通す。設定履歴の検査は値が入力に現れるか、納品書の検査は予測した受入数から導かれる差異と回答が一致するかを確認する。誤った値がこの検査を通る件数も報告する。レビューと指摘付きレビューは同じ初回回答を共有し、検査が発火した同じ問題でも比較する。

両モデルは実機の同じApple Terminal、OS付属fm、greedy、毎回の新規セッション、並列度1で実行する。問題と方式の順を固定乱数で並べ、同じ方式のモデルの実行順を交互に変える。PCCは各要求前後に枠を確認し、上限間近または到達で当日の送信を止める。出力ごとに入力ハッシュ・経路・時間・枠状態を保存する。推論時に読み込むのは公開入力と位置付きOCRだけで、正解は別ファイルに置く。起動時のロック検証は正解ファイルをバイト列としてハッシュする。

待ち時間は各方式を単独で使う場合に必要なCLI実時間の合計に、入力の用意、通常コードの後処理、該当時のVisionの実測時間を足す。Visionは画像ごとに一度実行し、同じ文字認識結果を全方式に与え、その時間を利用する各方式に計上する。前後の枠照会、オフライン採点、試験のチェックポイント管理は含めない。初回表示は最初の呼び出しの標準出力を観測した時刻である。実生成トークン数はCLIが返した場合のみ残す。

小規模な合成パネルの対比較として、正答数、改善した問題数と悪化した問題数、呼び出し数、中央値を公表する。複数方式の試行で共有した応答を二重に送信しない。構成条件やログに登場する語彙、納品書の帳票レイアウトが異なる実務全体への一般化は別の評価課題とする。
