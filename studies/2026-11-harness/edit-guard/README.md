# 表の誤適用を防ぐには何を検査するか

東窓口だけの依頼で西窓口まで書き換える、現在値が条件に合わなくても新しい値にする。前回の表編集で残った4件の誤適用を、AFM 3 Core Advancedと合成表で再検証した。依頼から対象行を特定し、AFMにはその行の数値だけを提案させ、書き込む直前に現在値と条件を照合した。前回の12件は全件正しく完了した。新しい有効な依頼24件では誤適用が4件から0件になり、正しい完了は17件で同数だった。[前回の試験](../findings.md)・[ケース別の最終状態](results/outcomes.jsonl)

## 方式別の結果

各欄の数字は **正しく完了 / 誤適用 / 保留**。現在値が条件に合わず、その値を維持すると正しく判断したものも完了に含める。要確認の8件では保留が正しい処理になる。意図と違うまま無変更で完了扱いした件数は、今回の全方式で0件だった。[集計と保留理由](results/summary.json)

| 方式 | 前回の依頼 12件 | 新しい有効な依頼 24件 | 要確認の依頼 8件 |
|---|---:|---:|---:|
| 表全体から差分を提案し、競合時に再読 | 8 / 4 / 0 | 17 / 4 / 3 | 0 / 7 / 1 |
| 同じ提案の対象行と件数を検査 | 7 / 2 / 3 | 15 / 1 / 8 | 0 / 0 / 8 |
| 同じ提案の対象行・条件・更新値を検査 | 7 / 0 / 5 | 15 / 0 / 9 | 0 / 0 / 8 |
| **AFMに1行だけで提案させ、条件と更新値を検査** | **12 / 0 / 0** | **17 / 0 / 7** | **0 / 0 / 8** |
| 通常コードで依頼を解釈して計算 | 12 / 0 / 0 | 20 / 0 / 4 | 0 / 0 / 8 |

前回の12件では、モデルに表全体を直接書き直させると正しく完了したのは4件、誤適用は8件だった。今回の比較基準には、それより成績が良かった「差分＋再読」を使った。保存済みの21応答を再生し、12件すべてで元の最終状態と判定が一致した。[前回のケース別結果](../edits/results/outcomes.jsonl)・[元の応答](../edits/results/calls.jsonl)

## 保留と修正で何が変わったか

- **対象外の行への書き込み**。過去の `edit-07` と `edit-10` では、依頼された東窓口の値は正しかったが、西・北窓口の値まで変わった。1行方式では対象の区画と数値欄をコードが決め、他の行をAFMに渡さない。両方とも東窓口だけ更新できた。[旧入力](../edits/fixtures/inputs.jsonl)・[最終状態](results/outcomes.jsonl)
- **読んだ後に変わった現在値**。過去の `edit-09` は「15のときだけ19に変更」だった。更新直前には17になっていたが、以前の方式は19を書いた。今回は競合時に読み直し、条件を確認して17を保持した。`edit-12` も同じ処理で解決した。[最終状態と呼び出し履歴](results/outcomes.jsonl)
- **検査を足すだけで止まる正しい更新**。`edit-01` の差分は東窓口を7から10にし、西・北窓口には元と同じ値を書こうとしていた。差分全体の検査は3行の提案を保留した。1行方式では東窓口を10にできた。[旧モデル出力](../edits/results/calls.jsonl)・[新モデル出力](results/calls.jsonl)
- **新しい24件での取りこぼし**。1行方式で新たに完了したのは3件、以前は正解だったのに保留になったのも3件だった。保留7件の内訳は、対応していない言い回しが4件、AFMの提案値が計算と一致しなかったものが3件。`request-05` では「保管数を2加算」に対して、再読後の9から10にする案が返り、書き込みを止めた。「2を上乗せしてください」も意味は明確だが、事前に固定した文法では扱えず保留になった。[依頼と観測時の表](fixtures/inputs.jsonl)・[新モデル出力](results/calls.jsonl)
- **対象を確定できない依頼**。要確認の8件は、区画や欄の重複、対象の省略、量の未指定、相反する指示、複数箇所の依頼、結果が負数になる減算を含む。1行方式は8件ともモデルを呼ばず保留した。[要確認の入力と期待結果](fixtures/answers.jsonl)

有効な新規24件で、差分＋再読は計42回のモデル呼び出しを使い、1件あたりの処理時間中央値は1.00秒だった。1行方式は30回、0.37秒だった。この時間は各ケースで使用した実測CLI時間と、保存応答を使って再生した検査・適用時間の合計である。定型の数値更新に限れば、通常コードがモデル呼び出し0回で20件を完了し、4件を保留した。[方式別の時間と回数](results/summary.json)

## テストアプリの使い方

`checked` は既存のAFMの差分提案を検査する。対象行と旧行が一致し、依頼の条件から計算した新値と一致した場合にだけ結果を返す。例では条件が外れているため、結果は `held`、理由は `condition_not_met` で、持出枠は17のままになる。リポジトリのルートから実行する。

```sh
cd studies/2026-11-harness/edit-guard
python3 -B apply_edit.py --method checked <<'JSON'
{
  "id": "example-1",
  "ticket": "北窓口の持出枠が15のときだけ19に変更。違えば現在値を維持。",
  "lines": ["[北窓口]", "持出枠=17"],
  "proposal": {"edits": [{"section": "[北窓口]", "old": "持出枠=17", "new": "持出枠=19"}]}
}
JSON
```

`scoped` は対象の1行をCore Advancedに渡す。次の例では東窓口を10に更新し、西窓口の7を維持した。定型の依頼をコードだけで処理する場合は、同じ入力で `--method rules` を指定できる。

```sh
python3 -B apply_edit.py --method scoped <<'JSON'
{
  "id": "example-2",
  "ticket": "東窓口の予約枠を、反映時点の値から3増やす。",
  "lines": ["[東窓口]", "予約枠=7", "[西窓口]", "予約枠=7"]
}
JSON
```

出力の `status` は更新成立なら `applied`、条件を確認した結果として現状維持なら `noop`、人の確認が必要なら `held`。テストアプリはメモリ上の表を処理し、更新後の全行を標準出力に返す。同じプロセスで `Sheet` を共有すると、読み直し、更新直前の版の照合、完了した同一要求の二重適用防止が働く。CLIを起動し直すと版番号と要求履歴は初期化される。[適用処理](guard.py)・[CLI](apply_edit.py)

## 測定条件と再現

2026年11月24日、Mac mini M6、メモリ32 GB、モデル配置先は内蔵SSD 256 GB、macOS 27.2.1（26B131）。検証データは外付けSSDに置いた。OS付属の `fm` で `system` がAFM 3 Core Advancedを示すことを確認し、greedy、新規セッション、同時1件で新たに102回生成した。PCCは当日分の利用枠に達していた。24件は4種類の演算と各6通りの表現を組み合わせた合成問題で、自由形式の表や一般の日本語依頼への誤適用率は今回の測定範囲外である。[実行記録](results/run.json)・[事前に固定した設計](design.md)・[入力とコードのハッシュ](lock.json)

公開結果の再採点と回帰テストは、Python 3.9以上で実行できる。保存した102応答と前回の21応答から44件×5方式を再現する。回帰テストには72通りの壊れた差分、二重要求、値が一度変わって元に戻る競合を含む。

```sh
python3 -B study.py verify
python3 -B test_guard.py
```

対応するMacのApple Terminalから次を実行すると、Core Advancedであらためて生成する。生成結果は `build/session/results/` に保存され、同じフォルダで再開すれば完了済みの要求を再利用する。

```sh
zsh './Run Edit Guard.command'
python3 -B study.py verify --results build/session/results
```
